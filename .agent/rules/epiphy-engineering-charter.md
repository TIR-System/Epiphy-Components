# Epiphy 工程宪章与强制研发流程 (Engineering Charter)

> **适用范围**：本规则对接入本仓库的任何 AI 协作者与人类开发者强制生效，并由 `./gradlew check` 中的 `EngineeringCharterGuardTest` 在编译测试期执行自动化校验。

## 1. 强制前置拆解流程：「底层机制 ➔ 通用能力 ➔ 下游案例」

在修复任何缺陷、优化性能或新增功能前，**严禁直接针对具体报错表象、某张截图或某件测试道具去修补核心模块（`epiphy-api`、`epiphy-core` 及 `kubejs/*/通用组件/`）**。

动笔修改代码前，必须按以下四步完成问题降维：

1. **表层现象（Symptom）**：记录在哪个具体测试场景观察到了什么现象（例如某件测试物品的光环被贴图遮挡、某段富文本帧率下降）。
2. **底层机制归因（Mechanism — 禁止出现任何具体道具/玩法词汇）**：将问题还原为通用图形管线、缓冲提交时序、状态机转换、线程可见性或存储 I/O 机制（例如 `MultiBufferSource` 延迟固定缓冲与流式自定义 `RenderType` 的提交顺序未隔离）。
3. **通用能力契约与已知边界（Capability & Boundaries）**：核心层应提供什么参数化原语或状态契约？成立的前置条件是什么（如调用线程、OpenGL 状态假设）？在什么边界下不适用或会退化？
4. **下游案例消费（Downstream Case）**：仅在案例层（如 `kubejs/*/小玩意与案例/` 或独立演示包）通过公开配置调用该能力；核心层源码、默认值、API 命名与注释对下游案例保持完全无感知。

**机器门禁**：`EngineeringCharterGuardTest` 会自动扫描案例目录中注册的物品 ID、预设 ID、着色器名与贴图标识，连同具象器械部位词表（如剑、刀、刃、护手等），反向检查 `epiphy-api`、`epiphy-core` 与 `通用组件`；一旦出现案例概念倒灌，构建直接失败。

## 2. 默认不完美原则与平实自然的注释规范

必须默认自己编写的代码**存在未覆盖的边界或潜在缺陷**。代码注释与工程文档的目标是帮助阅读者准确理解**代码做了什么、为什么这么做、在什么条件下会失效**，绝不是向阅读者“推销”代码有多好。

### 2.1 写作要求（自然语言 + 诚实边界）
- **保持流畅自然的陈述句**：用平实、好读的自然语言解释设计意图、协作关系和关键步骤，让接手者顺畅读懂来龙去脉，不要写成生硬的口号或堆砌修辞。
- **如实交代已知边界与折中**：核心子系统的类注释应自然说明其前置条件与当前已知限制（例如：“仅限客户端渲染线程调用”、“分桶按 32px 对齐会产生少量边缘显存留白”、“若外部提前中断渲染流需依赖下一次界面切换清理”）。尚未实现的保护能力绝不可在注释中提前宣称已经具备。

### 2.2 严禁出现的说服性与绝对化措辞
<!-- charter-banned-examples-start -->
以下类型的自夸、营销修辞或绝对化承诺在源码注释与主干技术文档中一律禁止（由 `EngineeringCharterGuardTest` 自动扫描拦截）：
- 主观吹捧与情绪化修饰：`铁桶`、`无懈可击`、`完美`、`极速`、`极致`、`黑科技`、`丝滑`、`连根拔除`、`bulletproof`、`flawless`、`blazingly fast`；
- 掩盖边界的绝对化断言：`绝对恢复`、`绝对安全`、`彻底根治`、`彻底消除`、`彻底告别`、`零损耗`、`零开销`、`永不`、`100% 安全 / 100% 零泄漏 / 100% 兼容`、`zero-overhead`。

## 3. 性能指标与实机测量五元组协议

没有绑定测量方法与环境条件的毫秒/纳秒数字只是主观声明，不具备工程参考价值。

1. **禁止书写无测量上下文的裸耗时承诺**：
   <!-- charter-banned-examples-start -->
   禁止在源码注释或里程碑验收条件中直接写 `< 0.08 ms`、`<= 0.4 ms`、`< 1ns` 等缺乏测试协议支撑的数字断言。
   <!-- charter-banned-examples-end -->
2. **CI 自动化门禁优先验证「确定性结构不变量」**：
   在 `./gradlew check` 中，用与硬件配置无关的结构指标作为验收标准——例如同一深度阶段内跨 $K$ 张纹理图集页时 `MultiBufferSource.getBuffer` 的调用次数上界、单次场景跨界调用次数、是否误刷外层共享缓冲等。
3. **实机耗时报告必须附带「测量五元组」**：
   凡在文档或测试记录中引用具体耗时数据，必须注明：
   - **计时边界**：明确是渲染线程 CPU 提交段耗时（`System.nanoTime()` 包裹顶点计算与缓冲写入，不含 GPU 异步光栅化），还是 OpenGL `GL_TIME_ELAPSED` GPU 查询耗时；
   - **分辨率与缩放**：窗口像素宽高与 `GUI Scale`（如 `1920x1080 @ GUI Scale 2` vs `3840x2160 @ GUI Scale 4`）；
   - **管线栈环境**：纯原版 `BufferBuilder` / 是否安装 `ModernUI`（是否开启 SDF）/ 是否安装 `Iris` 及是否开启具体光影包（开启光影后顶点格式与缓冲刷写路径完全不同）；
   - **负载规模**：并发活跃实例数、可见字符/顶点数、描边采样档位；
   - **统计分布**：连续采样不少于 300 帧后的 `Avg / P95 / P99 / Max`。

## 4. 版本单一真值源（SSOT）与数据安全红线

1. **版本真值源**：
   - 原生模组版本号以 [`gradle.properties`](../../gradle.properties) 中的 `mod_version` 为唯一真值源，禁止在业务代码中重复硬编码失步字符串；
   - 协议与别名契约版本以 [`docs/proto_v6_schema.json`](../../docs/proto_v6_schema.json) 的 `schemaVersion` 为唯一真值源。
2. **存储隔离红线**：
   - 权限授权、撤销墓碑、认证模式与模组全局配置必须存放在 `<gameDir>/epiphy-data/` 或 `<gameDir>/config/` 下，严禁存放在 `saves/<world>/` 世界存档内部，亦不得从存档内部导入权限配置。
3. **改动验证**：
   - 修改代码、注释或文档后，必须运行 `./gradlew check` 确认协议契约、字节码双端隔离、无 Kotlin 标准库捆绑及工程宪章门禁全部通过；
   - Git 提交信息遵循双语格式：`<subject> [(<scope>)] <中文说明> | <English description>`。
